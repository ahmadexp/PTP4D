# PTP4D 0.5 development: local validation

Historical pre-hardware validation. See the later
[six-servo hardware trials](servo-20261120/) and
[0.5 release build validation](v0.5-release.md) for the published release.

Validated on 2026-11-19. This is local build and simulation evidence, not a new
physical PTP or UTC-accuracy measurement. The published 0.4 executable, photos,
screenshots and timestamp evidence were preserved.

## Build

- Borland C++ 3.1, huge model, DOS CRLF source files.
- DOSBox-X 2026.10.01, CPU type 486, FPU emulation disabled.
- Product and four DOS test builds completed without compiler warnings.
- Development executable: `build/PTP4D.EXE`, 77,432 bytes.
- SHA-256: `98d40271b5c09c3b28c1cc5966b3e900aed19bec22db1685ba007ad91563d002`.
- Help and missing-driver probes passed. Unsupported DOS-derived GM mode was
  refused before a driver probe. All controller, calendar, options and MIDI
  tests ran successfully in the no-FPU DOS environment.

The development executable is a local build artifact. `bin/PTP4D.EXE` remains
the released 0.4 binary. No compiler or private firmware was added to the source
repository, and no new executable was installed on the PC110.

## Native suite

`python3 tools/test.py` passed with C89, warnings as errors, AddressSanitizer and
UndefinedBehaviorSanitizer:

- Original mailbox/identity/transport and MIDI framing/CRC tests.
- Every selector and direction, legacy defaults, malformed arguments,
  incompatible roles, and required civil-time assertions.
- Five host controllers with both drift signs, noise, nonuniform sample periods,
  saturation, phase steps, oscillator changes, missing intervals and timestamp
  wrap. These deterministic models do not rank physical servo performance.
- Every supported Gregorian date, including year 2000 and dates after 2038;
  UTC/TAI/local offsets; invalid and overflowing epochs; capture latency;
  midnight and intentional-clock-write deadline rebasing.
- Extended MIDI command layout and correlated ACK rejection. Exact expected
  addend checked at every integer correction from -100,000 to +100,000 ppb.
- 27 executions of the actual DOS session code using fake MIDI and DOS services:
  all six follower selections, free-running GM, capability failure, rejected
  correction, generation replacement, GM timestamp error, missing STOP,
  unqualified time, invalid epoch/state, setter failure, repeated tracking
  corrections, validity expiry, clock jump, source absence/loss, corrupt or
  mismatched ACKs, excessive capture latency, lost START ACK, and generation
  replacement during a capture.
- Eight Python host-tool and historical-evidence checks.

## Remaining physical validation

Hardware integration is deferred until shared storage-transfer work releases
the devices. No PC110/Pico reset, SD ownership change, USB-role change, PTP run,
firmware write, remote serial access, or transfer-state edit was performed.

The new host controllers and PHC2DOS path still need real 486SX CPU/watchdog
timing, installed-firmware capability checks, USB latency measurements, clock
step/tracking and DOS/RTC behavior tests. Epoch and UTC validity require a
separately established source. DOS-derived GM service remains unsupported by
the inspected protocol; its necessary firmware changes are listed in the
[protocol audit](../servo-inventory.md).
